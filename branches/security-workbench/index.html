Der Prüfplatz.

01 / VERSIONSVERGLEICH

Welche Laufzeit verarbeitet die Daten?

Browser: deklarierte Version. CLI: tatsächlich gestarteter Prozess. In Node können Sicherheitskorrekturen zurückportiert sein, obwohl die angezeigte Brotli-Version gleich bleibt.

Strukturierte Ausgabe


02 / ECHTE URL-API
Ist es durchgehend dieselbe Identität?
Der Browser berechnet die WHATWG-URL. Daneben steht eine ausdrücklich enge ASCII-Host-Policy. Resolver und echte Verbindung bleiben eigene Prüfstellen.
Codepunkte und Parser-Ergebnis


03 / ENDLICHES DECODER-MODELL
Fehler oder noch unvollständig?
Dieselben drei Ereignisse: Daten, ungültiger Block, weitere Daten. Der korrigierte Pfad beendet die Verarbeitung am Formatfehler.
Das Modell verarbeitet Ereignisnamen. Es enthält keinen nativen Brotli-Exploit.
Modellspur


04 / SYNTHETISCHE ZUGRIFFSKONTROLLE
Passt das geladene Objekt zum Subjekt?
Angemeldet ist Alice. Die Auswahl steuert das Objekt, auf das zugegriffen werden soll. Eine Gegenprobe zeigt den absichtlich fehlerhaften Pfad.
Feste Beispieldaten. Den gleichen Vergleich führt der CLI-Selbsttest über echte lokale HTTP-Requests aus.
Entscheidung


05 / ANFRAGEBUDGET-MODELL
Wie viel darf gleichzeitig weiter?
Ein Tokenbudget erlaubt eine begrenzte Anzahl Ereignisse und füllt sich mit Modellzeit nach. Jeder Balken steht für ein berechnetes Ereignis.
Keine Netzlast. Im lokalen HTTP-Labor folgt nach dem festen Requestbudget eine echte 429-Antwort.
Budget und Zeitpunkte


06 / STATISCHE TEXTSICHTUNG
Was ist beobachtet, was bleibt offen?
Codeverweise finden und ihren exakten Textspan zeigen. Ein Kommentar kann denselben Treffer auslösen wie ausführbarer Code.
Die Probe wird als Text gelesen. Ein Treffer ist ein Prüfhinweis; die Klassifikation bleibt offen.
Fundstellen




EIGENER ENDPOINT · ECHTE HTTP-ANTWORTEN
Mit Burp direkt
an die Grenze.
Ein Übungsdienst bindet ausschließlich an 127.0.0.1. Alice, Bob und ihre Dokumente sind synthetisch. Du erhältst eine lokale Adresse und einen kurzlebigen Laborschlüssel.
Requests im eigenen Burp-Projekt prüfen: fehlender Schlüssel → 401, eigenes Objekt → 200, anderes Subjekt → 403, verbrauchtes Budget → 429.
Im Programm zählt danach dessen aktuelle Policy: exakte Assets, Testkonto, erlaubte Verfahren und Lastgrenzen. Die Freigabe dieses lokalen Labors überträgt sich auf dein nächstes Ziel erst durch dessen eigene Autorisierung.
Offizielle Burp-Anleitung zum Zielbereich ↗
Im geklonten Repository
Node.js mit aktuellem Sicherheitspatch verwenden. Keine zusätzlichen Pakete erforderlich.
node branches/security-workbench/cli.mjs runtime --require-patch
node branches/security-workbench/cli.mjs identity 0127.0.0.1
node branches/security-workbench/cli.mjs selftest
node branches/security-workbench/cli.mjs lab
Selbsttest: 14 sequenzielle Requests gegen zwei selbst erzeugte Loopback-Fixtures. Ein fehlerhafter und ein korrigierter Kontrollpfad; danach werden die Listener geschlossen.
Labormodus: 15 Minuten, eigener Schlüssel, feste Route, maximal 64 freigegebene Requests. Beenden mit Strg+C. CLI-Ausgaben und Schlüssel bleiben auf deinem Rechner.
